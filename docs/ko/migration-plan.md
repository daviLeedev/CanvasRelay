# CanvasRelay 마이그레이션 계획

[English](../migration-plan.md) | **한국어**

| 항목 | 값 |
| --- | --- |
| 상태 | 초안 |
| 전략 | 깨끗한 공개 저장소, 수직 기능 단위, 기존 런타임 병행 |
| 최종 수정 | 2026-07-31 |

## 1. 목표

비공개 로컬 스튜디오에서 검증된 제품 동작을 공개되고 검토 가능한 Next.js와
FastAPI 모노레포로 이전한다. 비공개 데이터, 인증정보, 공급자 우회 구현,
모델 파일, 기존 프론트엔드 구조는 복사하지 않는다.

목표는 코드 한 줄 단위의 동일성이 아니다. 가장 어려운 엔지니어링 작업을
보여주는 더 작고 일관되며 실행 가능한 포트폴리오 제품을 만드는 것이다.

## 2. 기존 기준선

계획 시점의 비공개 애플리케이션은 다음으로 구성되어 있다.

- Jinja2 템플릿과 정적 파일을 제공하는 FastAPI 백엔드.
- 약 2,649줄의 단일 Jinja2 페이지.
- 약 9,141줄의 단일 주요 Vanilla JavaScript 파일.
- 약 5,144줄의 스타일시트.
- 약 50개의 FastAPI 라우트 선언.
- 46개의 테스트 파일과 다수의 비공개 모델 워크플로.
- 공개 저장소에 들어가면 안 되는 로컬 로그, 미디어, 사용자 설정, 장치별
  절대 경로.

이 수치는 마이그레이션 위험을 설명할 뿐 재현해야 하는 목표가 아니다.

## 3. 마이그레이션 원칙

1. **깨끗한 공개 이력.** 검토된 개념과 일반화된 코드만 다시 작성하거나
   복사한다.
2. **수직 기능 단위.** 다음 기능으로 이동하기 전에 UI, API, 영속성,
   테스트를 관통하는 하나의 유용한 흐름을 완성한다.
3. **Strangler 마이그레이션.** 공개 기능이 완료 기준에 도달할 때까지
   비공개 애플리케이션을 계속 사용할 수 있게 한다.
4. **계약 우선.** UI 로직을 옮기기 전에 정규화된 API 스키마를 안정화한다.
5. **Mock 우선.** 실제 공급자를 연결하기 전에 결정적 데모 모드로 각
   기능을 완성한다.
6. **의미 없는 동일성 금지.** 기존 토글 전부가 아니라 제품 가치를 옮긴다.
7. **점진적 3D 향상.** 각 이머시브 표현과 함께 또는 그 전에 기능적인
   DOM UI를 완성한다.
8. **작고 검토 가능한 변경.** 하나의 거대한 자동 생성 커밋을 피한다.

## 4. 공개 경계 감사

구현을 복사하기 전에 기존 자료를 분류한다.

| 분류 | 공개 처리 방식 |
| --- | --- |
| 일반 도메인 로직 | 검토와 테스트 후 다시 작성하거나 복사 |
| 공급자 API 어댑터 | 문서화되고 검증 가능한 연동만 포함 |
| 비공개 워크플로 JSON | 제외하고 안전한 설명용 fixture 제공 |
| 모델 가중치와 LoRA 파일 | 제외하고 선택적 배치 경로만 문서화 |
| 생성 미디어와 캐릭터 레퍼런스 | 제외하고 검토된 샘플 자산 사용 |
| `.env`, OAuth 파일, 토큰 | 제외하고 다른 이력에 커밋됐다면 교체 |
| 로그와 절대 경로 | 제외하고 예시에서도 가림 처리 |

마이그레이션 코드가 포함된 첫 push 전에 비밀정보와 대용량 파일 검사를
수행한다.

## 5. 목표 마일스톤

### Phase 0: 제품과 아키텍처 기준선

결과물:

- 제품 브리프, 아키텍처, 마이그레이션 계획, ADR 0001.
- 공개 범위와 비목표.
- 초기 도메인 용어와 라우트 구조.
- 보안 경계와 데모 모드 요구사항.

완료 기준:

- 네 문서가 서로 모순되지 않는다.
- 문서만 읽고도 제품과 런타임 구성을 설명할 수 있다.
- 비공개 구현이나 자산을 복사하지 않았다.

### Phase 1: 모노레포 기반

결과물:

- Next.js App Router, TypeScript, lint, 테스트를 갖춘 `apps/web`.
- FastAPI, Pytest, health endpoint, 설정 모델을 갖춘 `apps/api`.
- 루트 스크립트, `.env.example`, 포맷팅, GitHub Actions.
- Docker Compose 데모 프로필.
- OpenAPI 내보내기와 생성된 TypeScript 계약 검사.

완료 기준:

- 새 기여자가 문서화된 명령으로 web과 API를 실행할 수 있다.
- 인증정보가 없는 clone에서 CI가 통과한다.
- `/api/v1/health`를 타입이 있는 웹 클라이언트로 호출한다.

### Phase 2: 제품 셸과 3D 기술 검증

결과물:

- 반응형 스튜디오 셸, 사이드바, 상단 상태, 라우트 오류 경계.
- 디자인 토큰과 접근 가능한 폼 및 컨트롤 기본 요소.
- 결정적 Mock 작업을 사용하는 클라이언트 전용 React Three Fiber 장면.
- 2D/3D 표시 선택 저장과 모션 감소 동작.
- 데스크톱, 태블릿, 모바일 시각 테스트.

완료 기준:

- 세 개의 Mock 작업이 대기, 실행, 완료로 전환되는 모습이 보인다.
- 같은 작업을 2D 모드에서도 완전히 사용할 수 있다.
- 캔버스가 비어 있지 않고 올바르게 프레이밍되며 unmount 시 리소스를
  해제한다.
- 폼과 탐색은 3D 번들을 로드하지 않아도 사용할 수 있다.

### Phase 3: 이미지 생성 수직 기능

결과물:

- 프롬프트, 네거티브 프롬프트, 이미지 업로드, 공급자, 프리셋, 파라미터.
- `text_to_image`와 `image_to_image`를 위한 `POST /api/v1/jobs`.
- Mock 이미지 공급자와 변경 불가능한 요청 스냅샷.
- 큰 결과 미리보기와 안전한 미디어 영속화.
- 단위, API 통합, Playwright 성공 및 실패 테스트.

완료 기준:

- 리뷰어가 Mock 이미지를 제출, 관찰, 검사, 재사용할 수 있다.
- 비어 있거나 잘못되거나 의도적으로 실패한 결과가 정규화된 오류를 낸다.
- 새로고침이 선택 결과와 실행 중인 작업을 혼동하지 않는다.

### Phase 4: 작업 센터와 미디어 라이브러리

결과물:

- 작업 목록, 상세, 취소, 재시도, polling 대체가 있는 SSE 업데이트.
- 라이브러리 필터, 밀도, 선택 및 삭제 모드, 상세 보기.
- 프롬프트, 모델, 공급자, 파라미터, 레퍼런스, 시각을 포함한 생성 이력.
- 같은 자산 선택 모델을 사용하는 선택적 공간 비교 보기.

완료 기준:

- 대기 작업을 취소하고 실패 작업을 재시도할 수 있다.
- 종료 결과가 페이지 새로고침 없이 반영된다.
- 페이지네이션으로 이전에 불러온 자산이 잘못 사라지지 않는다.
- 삭제는 선택한 메타데이터와 소유 파일을 제거하지만 다른 레코드가
  참조하는 업로드는 제거하지 않는다.

### Phase 5: 영상 생성 수직 기능

결과물:

- Image-to-video 요청 편집기와 영상별 파라미터 스키마.
- 대기, 샘플링, 인코딩, 영속화 단계를 가진 Mock 영상 공급자.
- 반복 미리보기, 썸네일, 메타데이터, 라이브러리 재사용.
- 취소와 timeout 의미의 문서화 및 테스트.

완료 기준:

- 라이브러리 이미지에서 소스 경로 누락 없이 영상 요청을 시작한다.
- 결과 영상과 썸네일이 이전 공급자 이력이 아니라 제출한 작업에 속한다.
- 영상 길이와 프레임 메타데이터가 저장된 결과물과 일치한다.

### Phase 6: 프롬프트 코파일럿과 시스템 상태

결과물:

- 프롬프트 제안 어댑터와 매번 새 프롬프트를 만드는 동작.
- 프롬프트 및 네거티브 프롬프트 삽입 액션.
- 공급자, API, 저장소, 선택적 추론 서버 상태.
- 가려진 최근 오류와 요청 ID.

완료 기준:

- 브라우저 응답이나 애플리케이션 로그에 원본 인증정보가 없다.
- 코파일럿은 선택적이며 오프라인이어도 생성 기능을 사용할 수 있다.

### Phase 7: 실제 공급자 어댑터

결과물:

- 작고 안전한 기준 워크플로를 사용하는 선택적 ComfyUI 어댑터.
- 지원 작업과 파라미터 제한을 설명하는 기능 descriptor.
- 정리된 fixture를 이용한 공급자 계약 테스트.
- 필수 자산과 선택 자산을 분리한 설치 문서.

완료 기준:

- 데모 CI가 ComfyUI와 독립적으로 동작한다.
- 공급자 파싱이 null, 빈 값, 지연, 예상하지 못한 응답을 처리한다.
- 제출한 공급자 작업 ID와 선언된 출력 노드로 결과를 수집한다.
- 공급자별 실패를 정규화된 도메인 오류로 변환한다.

### Phase 8: 포트폴리오 릴리스 강화

결과물:

- 제품 스크린샷, 짧은 데모, 아키텍처 도식, 실행 명령이 있는 README.
- 안전한 샘플 데모 라이브러리.
- 접근성과 키보드 검토.
- 성능 trace와 문서화된 3D 예산.
- 의존성, 라이선스, 비밀정보, 대용량 파일 감사.
- 태그된 `v0.1.0` 포트폴리오 릴리스.

완료 기준:

- 깨끗한 clone에서 문서화된 데모와 자동 검사를 완료한다.
- 개인 경로, 비밀정보, 모델 가중치, 라이선스 없는 샘플이 없다.
- README가 태그된 revision에서 실제 보이는 기능만 주장한다.

## 6. 기존 구조와 목표 구조 매핑

| 기존 책임 | 목표 위치 |
| --- | --- |
| Jinja 탭 마크업 | Next.js 라우트와 기능 컴포넌트 |
| 전역 DOM 조회와 이벤트 리스너 | 컴포넌트 이벤트와 기능 hook |
| 전역 변경 가능 요청 상태 | React Hook Form과 명시적 draft 스키마 |
| 하나의 스크립트 안 polling timer | TanStack Query와 중앙 event client |
| 인라인 공급자 분기 | FastAPI provider registry |
| JSON 응답 구조 가정 | Pydantic 스키마와 생성된 TS 타입 |
| 미디어 카드와 상세 모달 | 공유 media 기능 모듈 |
| localStorage 키 | 버전형 namespace preference repository |
| 누적된 CSS selector | token, primitive, 기능 범위 style |
| JSON 메타데이터 런타임 | SQLite repository와 일회성 importer |

## 7. 상태 마이그레이션

### 사용자 설정

- `canvasrelay:v1:*` namespace를 사용한다.
- 사용자 설정과 draft만 저장하고 서버 작업 사실은 저장하지 않는다.
- 저장 객체에 버전을 부여하고 초기화 방법을 제공한다.
- 표시 라벨이 아니라 공급자 ID를 저장한다.

### 미디어 메타데이터

- 새 스키마가 안정화된 후 정리된 기존 JSON을 위한 일회성 importer를
  만든다.
- 가져오는 동안 체크섬과 크기를 계산한다.
- 설정한 기존 미디어 루트 바깥의 경로는 거부한다.
- 일부 레코드를 건너뛰어도 전체 가져오기를 중단하지 않고 보고한다.

### 공급자 프리셋

- 명시적인 안전 기본값으로 공개 프리셋을 정의한다.
- 비공개 공급자나 워크플로 이름을 자동으로 가져오지 않는다.
- 기존 작업 생성 이력을 해석할 수 있게 프리셋에 버전을 부여한다.

## 8. 모든 기능의 완료 정의

- 사용자에게 보이는 로딩, 빈 상태, 성공, 오류, 재시도 상태가 있다.
- 데스크톱, 태블릿, 모바일 레이아웃을 검증한다.
- 필수 액션에 키보드와 스크린리더 라벨을 제공한다.
- Pydantic과 TypeScript 계약이 일치한다.
- 구현 세부사항이 아닌 도메인 결정을 단위 테스트한다.
- 데모 모드의 Playwright 흐름이 최소 하나 존재한다.
- 로그에 비밀정보 없이 요청 ID와 작업 ID가 있다.
- 문서와 스크린샷이 구현과 일치한다.
- 모든 3D 동작의 필수 액션을 2D에서도 사용할 수 있다.

## 9. 위험 목록

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| 모든 비공개 워크플로 이전 | 릴리스가 안정화되지 않음 | 대표 공급자를 선별하고 비목표 명시 |
| 큰 React 컴포넌트가 큰 Vanilla 파일을 대체 | 구조가 겉으로만 개선됨 | 기능 경계와 컴포넌트 검토 한계 적용 |
| 미디어 텍스처 WebGL 메모리 누수 | 브라우저와 GPU 불안정 | 하나의 캔버스, 명시적 해제, 숨김 중지, 진단 |
| 3D가 스크롤을 잡거나 설정을 가림 | 태블릿과 모바일 흐름 실패 | 포커스 기반 조작, DOM 오버레이, 필수 2D 모드 |
| API 계약 불일치 | 런타임 요청 실패 | 생성 타입과 CI 차이 검사 |
| 공급자 이전 이력을 현재 결과로 연결 | 잘못된 미디어 표시 | 제출 작업 ID와 출력 식별자로 수집 |
| 비밀정보나 개인 자산이 Git 이력에 포함 | 공개 노출 | 깨끗한 이력, 검사, 허용 목록 기반 이전 |
| 데모가 외부 인프라에 의존 | 리뷰어가 실행하지 못함 | 1급 결정적 Mock 공급자 |
| 대규모 이전이 비공개 사용을 막음 | 작동 중인 도구 손실 | 병행 런타임과 수직 전환 |

## 10. 권장 Pull Request 순서

1. `docs: define product, architecture, migration, and ADR`
2. `chore: scaffold Next.js and FastAPI monorepo`
3. `feat: add typed health contract and studio shell`
4. `feat: add accessible design primitives and responsive navigation`
5. `feat: visualize deterministic jobs in 2D and 3D`
6. `feat: complete mock image generation vertical slice`
7. `feat: add job center with cancel, retry, and events`
8. `feat: add media provenance and library workflows`

각 Pull Request는 독립적으로 이해할 수 있어야 하며 기본 브랜치를 항상 실행
가능한 상태로 유지한다.

## 11. 전환과 롤백

- 마이그레이션 중에는 비공개 스튜디오를 실사용 도구로 유지한다.
- 공개 라우트는 완료 기준을 통과한 뒤에만 대체 기능으로 간주한다.
- 공개 마이그레이션 과정에서 비공개 미디어나 설정을 제자리 수정하지 않는다.
- Importer는 기본적으로 dry run이며 별도의 공개 데이터베이스로 복사한다.
- 실제 공급자 어댑터에 회귀가 생겨도 기능 플래그를 통해 데모 모드와 다른
  공급자는 계속 사용할 수 있다.

## 12. 첫 구현 체크포인트

첫 코드 체크포인트의 범위는 의도적으로 작다.

1. Next.js와 FastAPI를 시작한다.
2. 타입이 있는 health 데이터를 조회한다.
3. 결정적인 Mock 작업 세 개를 제출한다.
4. 접근 가능한 2D 목록과 3D 생성 스테이지에서 상태 전환을 본다.
5. 실행 중인 작업 상태를 잃지 않고 완료된 Mock 자산을 선택한다.
6. lint, 타입 검사, 단위 테스트, build, Playwright 시나리오 하나를 실행한다.

이 체크포인트는 기존 공급자 워크플로를 옮기기 전에 아키텍처를 검증한다.
