# ADR 0001: 모노레포에서 Next.js와 FastAPI 사용

[English](../../adr/0001-nextjs-fastapi-monorepo.md) | **한국어**

| 항목 | 값 |
| --- | --- |
| 상태 | 제안됨 |
| 날짜 | 2026-07-31 |
| 결정 담당 | CanvasRelay 유지관리자 |

## 배경

CanvasRelay의 비공개 이전 프로젝트는 하나의 큰 Jinja2 템플릿, 큰 Vanilla
JavaScript 클라이언트, 큰 전역 스타일시트를 제공하는 Python FastAPI
애플리케이션이다. 로컬 추론, 오래 걸리는 작업, 미디어 영속성, 외부 공급자
연동에는 성공했지만, 프론트엔드 규모가 커지며 상태의 소유권과 기능 경계를
파악하기 어려워졌다.

공개 포트폴리오 버전은 다음을 충족해야 한다.

- 현재의 React와 TypeScript 엔지니어링 방식을 보여준다.
- Python 기반 오케스트레이션과 기존 로컬 AI 생태계를 보존한다.
- 프론트엔드와 백엔드 변경을 함께 검토할 수 있게 한다.
- 인증정보와 GPU가 없는 데모를 제공한다.
- WebGL을 필수로 만들지 않으면서 기능적인 Three.js 경험을 제공한다.
- 비공개 Git 이력, 워크플로, 자산, 설정을 가져오지 않는다.

## 결정

CanvasRelay는 다음을 포함하는 모노레포를 사용한다.

- TypeScript로 작성한 Next.js App Router 웹 애플리케이션.
- Python으로 작성한 FastAPI 오케스트레이션 API.
- CI에서 검사하는 OpenAPI 기반 TypeScript 계약.
- 공간 작업을 위한 클라이언트 전용 점진적 향상으로 React Three Fiber.
- 1급 런타임 프로필로 결정적 Mock 공급자.

브라우저는 모든 도메인 작업을 FastAPI에 요청한다. Next.js route handler는
생성 오케스트레이션을 중복 구현하거나 공급자 인증정보를 보유하지 않는다.

초기 저장소 구조는 다음과 같다.

```text
apps/web        Next.js UI와 이머시브 장면
apps/api        FastAPI 도메인, 서비스, 공급자, 저장소
packages/contracts
docs
```

## 결정 요인

1. 포트폴리오에서 React, TypeScript, routing, 상태 관리, 반응형 상호작용,
   테스트를 명확히 보여줘야 한다.
2. Python은 ComfyUI 연동, 미디어 처리, 기존 오케스트레이션 로직에 가장
   적합한 선택으로 유지된다.
3. 모노레포는 계약을 가로지르는 변경을 하나의 원자적 변경으로 만들고
   리뷰어가 찾기 쉽게 한다.
4. App Router는 레이아웃, 라우트별 로딩과 오류 경계, 공개 프로젝트 설명
   화면을 제공하면서 클라이언트 중심 작업 공간도 지원한다.
5. 3D 장면은 React 생명주기와 통합되어야 하고 서버 렌더링 및 도메인
   상태와 분리되어야 한다.
6. 공개 프로젝트는 비공개 인프라 없이 실행되어야 한다.

## 세부 결정

### Next.js를 웹 프레임워크로 사용한다

App Router와 TypeScript를 사용한다. 상호작용 중심 스튜디오 라우트는 브라우저
API와 즉시 입력이 필요한 위치에서 주로 client component를 사용한다. Server
component는 클라이언트 작업을 줄이거나 데이터 소유권을 명확히 할 때만 쓴다.

스튜디오에 SEO 또는 서버 렌더링이 필수라서 Next.js를 선택한 것은 아니다.
프로젝트 구조, routing, 프로덕션 관례, 포트폴리오에서 알아보기 쉬운 React
프레임워크라는 가치 때문에 선택한다.

### FastAPI를 도메인 경계로 유지한다

FastAPI의 책임은 다음과 같다.

- 공급자 인증정보와 기능 조회.
- 업로드 검증과 미디어 저장.
- 작업 생명주기, 취소, 재시도, 진행률 정규화.
- 공급자 요청 및 응답 변환.
- 영속성과 구조화된 운영 로그.

Next.js 프로세스 안에 두기 위해 추론 또는 공급자 오케스트레이션을 Node.js로
다시 작성하지 않는다.

### 저장소는 모노레포로 구성한다

웹과 API 코드는 하나의 검토와 문서화된 릴리스를 공유한다. 모노레포라고 해서
하나의 런타임 프로세스를 사용하는 것은 아니다. 웹과 API는 각각 빌드할 수
있고 독립적으로 배포하거나 시작할 수 있다.

### OpenAPI를 계약 원본으로 사용한다

Pydantic 요청 및 응답 모델이 OpenAPI를 생성한다. TypeScript 타입과 브라우저
클라이언트는 그 계약에서 생성한다. 생성 결과가 오래되면 CI가 실패한다.

두 개의 서로 다른 원본이 생기지 않게 수동으로 동일한 TypeScript와 Python
도메인 모델을 작성하지 않는다.

### 3D는 점진적 클라이언트 기능이다

React Three Fiber로 Three.js 장면 생명주기를 React 안에서 관리한다. 장면은
브라우저에서 동적으로 로드되고 도메인 상태를 투영한 데이터를 받으며
`selectAsset`, `focusJob` 같은 의미 있는 명령을 내보낸다.

WebGL 장면은 작업, 요청, 미디어 메타데이터, 삭제 액션을 소유하지 않는다.
모든 필수 작업은 접근 가능한 DOM UI에서도 사용할 수 있다.

### Demo 모드는 제품 프로필이다

Mock 공급자는 실제 어댑터와 같은 공급자 계약을 구현한다. 결정적 진행률,
성공, 실패, 취소, 재시도, 샘플 미디어를 지원한다. 자동 E2E 테스트는 이
프로필을 사용한다.

## 검토한 대안

### FastAPI, Jinja2, Vanilla JavaScript 유지

**장점**

- 마이그레이션 비용이 가장 낮다.
- 하나의 런타임이며 프론트엔드 빌드 도구가 필요 없다.
- 기존 동작을 그대로 유지한다.

**선택하지 않은 이유**

- 프론트엔드 상태 소유권과 컴포넌트 경계 문제가 해결되지 않는다.
- 목표로 하는 React와 TypeScript 역량을 보여주지 못한다.
- 상태 중심 3D 작업 공간을 추가하면 전역 결합도가 더 커진다.

### React, Vite, FastAPI

**장점**

- 더 작은 클라이언트 도구 체인.
- 클라이언트 중심 로컬 대시보드에 자연스럽다.
- 단순한 정적 배포.

**선택하지 않은 이유**

- CanvasRelay에는 구조화된 공개 프로젝트 화면, 중첩 레이아웃, 명시적인
  라우트별 로딩 및 오류 관례도 필요하다.
- Next.js는 스튜디오의 client-only 렌더링을 지원하면서 의도적인
  포트폴리오 기술 신호가 된다.

Next.js의 복잡성이 더 이상 가치를 제공하지 않으면 Vite를 대안으로 다시
검토할 수 있다.

### 전체 백엔드를 Next.js로 이동

**장점**

- 하나의 언어와 잠재적으로 하나의 배포 결과물.
- Next.js route handler 직접 사용.

**선택하지 않은 이유**

- 제품 이득 없이 성숙한 Python 연동과 테스트를 버리게 된다.
- AI 워크플로와 미디어 도구는 이미 Python 중심이다.
- 로컬 추론 오케스트레이션이 웹 렌더러와 결합되면 안 된다.

### 웹과 API를 별도 저장소로 분리

**장점**

- 독립적인 소유권과 릴리스 주기.
- 각 저장소가 작아진다.

**포트폴리오 단계에서 선택하지 않은 이유**

- 계약을 가로지르는 변경을 하나로 검토하기 어렵다.
- 하나의 프로젝트를 평가하는 리뷰어에게 설치와 탐색 경험이 나빠진다.
- 현재 팀과 릴리스 과정은 저장소 단위 분리를 요구하지 않는다.

### React Three Fiber 없이 Three.js 직접 사용

**장점**

- 명령형 제어가 자유롭고 렌더러 추상화가 없다.
- 독립 Three.js 예시를 재사용하기 쉽다.

**선택하지 않은 이유**

- 수동 장면 생명주기가 React 생명주기 옆에 존재하며 상태 소유권을 중복시킬
  가능성이 크다.
- 선택한 프론트엔드 구조에서는 React Three Fiber가 컴포넌트 구성과 정리를
  더 잘 지원한다.

## 결과

### 긍정적 결과

- 공개 저장소가 현대적인 프론트엔드와 Python 백엔드 작업을 함께 보여준다.
- 웹과 API 계약을 원자적으로 변경할 수 있다.
- 공급자 어댑터가 표현 계층과 분리된다.
- 3D 경험이 야심차더라도 제품 전체를 제어하지 않는다.
- Demo 모드가 검토와 CI를 결정적으로 만든다.
- 수직 마이그레이션 중에도 비공개 애플리케이션을 사용할 수 있다.

### 부정적 결과

- 기여자에게 Node.js와 Python 도구 체인이 모두 필요하다.
- 로컬 개발에서 최소 두 개의 애플리케이션 프로세스가 실행된다.
- OpenAPI 생성 동기화 단계가 추가된다.
- 클라이언트 중심 화면에서 Next.js가 프레임워크 복잡성을 더할 수 있다.
- Three.js가 번들, GPU, 테스트, 접근성 책임을 늘린다.
- 모노레포의 우발적 결합을 막기 위한 규율이 필요하다.

### 중립적 또는 수용한 트레이드오프

- 웹과 API는 저장소를 공유하지만 독립적으로 배포할 수 있다.
- 일부 기존 UI 동작은 의도적으로 제외한다.
- Server component 사용 자체가 목표는 아니다.
- 첫 공개 공급자 범위는 비공개 버전보다 훨씬 작다.

## 가드레일

- FastAPI만 공개 도메인 API 역할을 한다.
- 공급자 인증정보를 `NEXT_PUBLIC_*` 환경변수에 넣지 않는다.
- 웹 애플리케이션은 Python 내부가 아니라 생성된 계약을 import한다.
- 3D 번들은 라우트별로 분리하고 테스트된 2D 대체 화면을 갖는다.
- 실제 공급자 지원이 데모 모드 CI를 깨뜨릴 수 없다.
- 모델 파일, 비공개 생성 미디어, 로그, 개인 경로를 Git에서 제외한다.
- 이전한 모든 기능에 로딩, 실패, 재시도, 반응형 상태가 있다.

## 검증

첫 구현 체크포인트로 이 결정을 검증한다.

1. 문서화된 명령으로 두 애플리케이션을 시작한다.
2. 웹 클라이언트가 타입이 있는 FastAPI health 데이터를 사용한다.
3. 세 개의 Mock 작업이 미래의 공급자와 같은 API를 통해 진행된다.
4. 접근 가능한 2D 화면과 비어 있지 않은 상호작용 3D 스테이지에서 작업을
   표시한다.
5. CI가 Python 테스트, TypeScript 타입, 웹 테스트, build, 계약 최신성을
   검증한다.

이 체크포인트에서 Next.js에 도메인 상태나 공급자 로직을 중복해야 한다면
추가 마이그레이션 전에 경계를 바로잡는다.

## 재검토 조건

다음 상황에서는 ADR을 다시 검토한다.

- Next.js 서버 기능은 사용하지 않는데 개발을 실질적으로 복잡하게 만든다.
- 웹과 API에 독립적인 팀 또는 릴리스 이력이 필요해진다.
- OpenAPI 생성으로 필요한 공급자 스키마를 명확히 표현할 수 없다.
- 3D 장면이 대체 화면, 성능, 접근성 요구사항을 충족할 수 없다.
- 호스팅 아키텍처에 지속적인 분산 worker와 object storage가 필요해진다.

## 상태 전환

아키텍처 체크포인트가 통과하고 첫 실제 공급자를 이전하기 전에 이 ADR의
상태를 `제안됨`에서 `승인됨`으로 변경한다.
